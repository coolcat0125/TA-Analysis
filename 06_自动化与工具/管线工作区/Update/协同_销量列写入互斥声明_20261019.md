# 协同声明：底表写入互斥与串行化协议（2026-10-19）

> 本文件由「销量联动工作流」（DSH 本会话，Team Lead: lead）写入，供**并发会话**与后续接手者读取。
> 目的：避免两个会话对同一工作簿 `NEV公告参数汇总表_合并版（341~410批）.xlsx` 发生**丢失更新（lost update）**。

## 1. 事实认定

| 项 | 事实 |
|---|---|
| 工作簿 | `NEV公告参数汇总表_合并版（341~410批）.xlsx`（5,392 行 × 39 列，sha256 前缀 `224665E37744747E`） |
| 会话 A（本会话） | 销量联动：尾插列 39 `车系ID` / 40 `销量覆盖状态`，写列 35/36/37；行数不变 |
| 会话 B（并发） | `cr17_011_apply_rows.py`：411（正式公告）/412（公示）**新增行**追加至末尾 + 既有 411 行补空 |
| 双方共同风险 | 若两者同时 `load_workbook` → 后落盘者的整本 save 会**抹掉**前者全部改动 |

## 2. 已验证的现有护具（会话 B 侧，设计良好）

`cr17_011_apply_rows.py` 头注释与实现：

- **按列名映射**：「并发会话正在尾插『销量』类列（39→41），本脚本对列数自适应，绝不按下标盲写」→ `--expect-min-cols` 默认 39，容忍更多列。
- **自有列隔离**：`PEER_COLS = ("月销量(辆)", "销量数据月份", "销量更新日期")` —— 本脚本**绝不写入**会话 A 的列。
- **哈希守卫**：`--apply` 必须带 `--expect-sha <sha256>`，落盘前比对当前工作簿 sha，不等即 `[FATAL] 工作簿已被并发修改`。
- **自动备份**：`archive/v4.9.32_pre-411412_backup_<YYYYMMDD>.xlsx`。
- **只追加、只补空**：新增行追加末尾；既有 411 行仅补空值单元格，非空一律跳过并记录。

**结论：会话 B 的写入对会话 A 的列是安全的；剩下的唯一风险是「同一时刻双双 save」。**

## 3. 串行化协议（定案）

**顺序：会话 B（411/412 新增行）先落盘 → 会话 A（销量列）后落盘。**

理由：B 已有 sha 守卫且正在飞行中；A 的匹配计划是按行计算的，必须建立在**最终行集**之上。

### 3.1 会话 A 必须补齐的四项（对称护具）

1. **强制 sha 守卫**：`--apply --expect-sha <sha256>`，与 B 同构。sha 不等即中止，不得静默继续。
2. **落盘前整本备份**：`archive/v4.9.32_pre-sales_backup_<YYYYMMDD>.xlsx`（现有 JSON 备份只覆盖销量旧值，不足以回退整本）。
3. **行数不准硬编码**：`base_rows` 一律从工作簿实读；两个 JSON 均写入 `meta.base_rows` 与 `meta.base_table_sha256`（干跑所依据的 sha），六类状态和与四类分桶和必须等于**实际行数**。
4. **行身份复核**：`apply_to_workbook` 现行 `row_plan[i]` 位置式写入，落盘前必须按 `(批次, 产品型号)` 复核该行身份，不符即中止 —— 位置式写入遇到行集变化就是错位事故（AGENTS 2026-09-17 教训：单元格级回退必须 zip 行序配对）。

### 3.2 新增行（411/412）的销量归属

新增行必须**同样**获得 `销量覆盖状态` 取值，否则六类状态和 ≠ 行数、扩表自检失败。归属由常规匹配引擎判定：
- 若能锚定到 2026-09 在榜车系 → 正常写值；
- 否则按 `未匹配-已停产或未上量` / `未匹配-命名待锚定` 分桶，**留空不写 0**。

### 3.3 对交付物的连带影响（Lead 已认领）

行数若由 5,392 变为 5,392+Δ，以下必须同步：
- 扩表生成器自检里的 `base_rows == 5392` → 动态；
- 报告/演示稿核心数字（2,185 已匹配、40.52% 行级覆盖率、797,701 已锚定销量、68.61% 在榜覆盖率、73.05% 销售额占比、11.69× 行级重复倍数）→ 由 JSON 重取，禁止手写；
- 《核心论断与建议纲要》§结论 4 的「5,392 条公告记录（341~411 批）」→ 按新行数与批次范围改写，并披露有一批为**公示口径**（412 批，非正式公告）。
