## 3. 通道架构：三层采集执行器（抽离 Tabbit）

把「抓一个车系的全部款型参数」抽象为统一接口：`fetch_series(sid) → {series:{sid,name,brand}, cars:[{id,name,year,vals{…}}]}`。三个实现可插拔，上层管道无感。

### 层 A · 登录态直连（试点优先 → 目标主通道）

- 原理：HTTP GET 带**用户已登录会话的 cookie** + 桌面 UA + Referer，直拉 `https://www.dongchedi.com/auto/series/<sid>`，正则抽 `__NEXT_DATA__` JSON。无浏览器、无渲染、无签名需求。
- cookie 来源（三选一，均为用户自有会话）：①Tabbit 打开懂车帝后经 CDP `Network.getCookies` 导出（含 HttpOnly）；②Playwright 持久 profile 登录一次长期复用；③用户手动导出。
- **Wave 0 验收标准**（全过才升级为主通道）：连续 50 车系零封禁；字段集与浏览器通道样本（dcd_s4499 等 13 系）逐字段对拍一致；测出限流阈值与 cookie TTL（TTL 失效自动降级层 B 并告警）。
- 产能预估：2s/页礼貌限速，全量 ~1,000 车系 ≈ 35 分钟/全量轮——夜间自治完全可行。

### 层 B · 浏览器执行器（保底 + 映射发现，已验证）

- 既有 Tabbit 配方照旧：`tabbit-cli.exe nodejs --task dcd-params`，5 车系/180s，`jobs/b*` 任务 JS 已可生成。
- 同接口的替代实现（任一可用即可）：ZCode 内置浏览器（browser-use）、Playwright 持久 profile、并行会话的 dcd_auto 浏览器管线 v2（全链测试通过，落地后对接同一 ingest）。
- 专属职责：DCD **搜索页车系映射**（kw→sid，层 A 同样可做但浏览器更稳）、层 A cookie 导出、层 A 失败回退。

### 层 C · 双源互证（质量闸，非采集通道）

- 汽车之家 paramConf（限速 0.35~0.5s + 冷却 + 品牌守卫，通道已固化）：DCD 新增绿值抽 10% 互证；**红修（改值）必须双源一致**才动；MINIEV 代际修复模式（车系逐代取证）为范本。

### 合规边界（全层适用）

不绕验证码/滑块/签名；只用用户自有登录会话；限速 ≥2s/页、夜间错峰；数据仅用于本底表研究；遇风控即降级停车，不硬闯。

## 4. 数据管道（复用五段，扩展两点）

```
S1 缺口清单（已有 gap_inventory.json，按 §2.2 重分类）
```

**扩展点① 缺口重分类**：`dcd_batch_run.py plan` 环节增加单电机合法空置剔除（2,998 行转「结构性空置」标记）与 727 前置依赖单独成批——砍掉 31% 无效工作量，避免给单电机行灌假后电机。

**URL 口径**：批量采集用车系级 `/auto/series/<sid>`（一页载全系款型）；用户示例的 `/auto/params-carIds-x-<carId>` 是单款型视图，仅用于单款核对。
