# DCD 自动优化工作流 · 问题记录

> 2026-09-22 首次全流程执行期间发现的问题与观察。按状态分三档:**已修** / **待用户机器验证** / **待相关线核实**。
> 每条注明:现象、根因、处置、证据位置。

## 一、已修(本次执行中抓出并修复,均附回归验证)

### P1 短名误配:U5/01 被配到 EU5/哪吒N01,且校验放行 【严重】
- **现象**:from-mapping 批次里 `U5`(底表实为**爱驰飞碟U5**,JX6472UBEV)被配到 sid=4074(北京EU5),`01`(另一款爱驰)被配到 sid=2964(哪吒N01),`decide_series` 全部判 accept。
- **根因**(两条叠加):
  1. 包含判定对被包含侧没有长度下限——`'u5' ⊂ '北京eu5'`、`'01' ⊂ '哪吒n01'` 即通过;
  2. `brand_tokens()` 把**车系族名(车型名称)当作品牌令牌**,族名 `U5` 恰是 `北京EU5` 子串,品牌检查被自己人满足。
- **处置**:包含判定双向加长度下限(被包含侧 ≥3 字符,或为单个 CJK 字);品牌令牌**只从商标/企业名取**。
- **验证**:15 例人审复现 15/15;`U5→北京EU5`、`01→哪吒N01` 均转 reject;`EU5→北京EU5`、`唐→比亚迪唐`、`AION Y Plus→AION Y` 正当案例仍 accept。

### P2 状态词表不一致导致死循环 【严重】
- **现象**:主循环 b003~b016 反复选同一批 5 个车系,进度水恒不动。
- **根因**:`decide` 写入的状态是 `hold`(decide_series 返回值),而 `next-batch` 跳过名单里写的是 `held`——被 hold 的车系永远跳不掉。
- **处置**:统一词表为 `hold`;在 `DONE_STATUS` 定义处加注释固化,勿再改词形。
- **验证**:循环在 4 轮内正确终止于"本地数据穷尽"。

### P3 共享名严格品牌规则误伤子品牌
- **现象**:欧拉黑猫、比亚迪唐、AION S 被人审接受的正确车系,自动判定为 `hold`。
- **根因**:共享名走"必须命中断期品牌令牌"的严格规则,而商标/企业名令牌里没有子品牌(欧拉∈长城、AION∈广汽、唐∈比亚迪)。
- **处置**:共享名放行"车系名与关键词实质对应"的形态(全等 / series⊂kw 且 ≥3 字符 / kw⊂series 且 ≥3 字符 / 单 CJK 字且 kw 含品牌令牌);短名与部分包含仍须品牌令牌。
- **验证**:欧拉黑猫/比亚迪唐/AION S 转 accept;`EX3` 双候选(极狐/几何)仍正确 hold(歧义);U5/01 仍拦。

### P4 recent_fills 重复计数
- **现象**:32 格填充在看板"最近填充"里显示 64 条。
- **根因**:`_record_batch` 在 dry-run 与正式 apply 两次调用中都往 `recent_fills` 追加。
- **处置**:只有 `outcome=='applied'` 才记录(回退批的格已撤销,同样不记)。
- **验证**:去重后 32 条,与台账序号 46639~46670 一一对应。

### P5 写库窗用进程本地时间
- **现象**:沙箱(UTC)在 05:00 被判在禁写窗,拒绝写库。
- **根因**:`datetime.now()` 取进程时区,而项目纪律按用户所在时区(UTC+8)。
- **处置**:`local_now()` 按 `DCD_TZ_OFFSET`(默认 8)折算,不依赖 tzdata(Windows Python 常缺 IANA 库)。

### P6 队列把已抽取车系整个排除,其残余缺口被跳过
- **现象**:欧拉黑猫 21 格、宏光MINIEV 6 格等有缺口却不在队列,from-mapping 一轮即报"穷尽"。
- **根因**:`dcd_queue.py` 为免重复抽取,把 mapping 里 ok=true 的车系**整条排除**——但"已抽取"≠"无缺口"。
- **处置**:改为打 `already_extracted` 标记;普通模式跳过(免重复搜索),from-mapping 模式专门消化。队列 830→845 个车系、缺口 3650→3744 格。

### P7 from-mapping 自由子串匹配
- **现象**:`U5` 匹配到映射 kw `北汽EU5`(子串),`01` 匹配到 `哪吒N01`。
- **处置**:改**前缀锚定**(part 与人审 kw 互为前缀,或 len≥3 时 part⊂series),并**沿用人审 kw 作为搜索词**(底表裸 part 常不是有效搜索词,如 `01`)。
- **遗留**:`Polestar 2`(人审 kw)与底表 `极星2`(中文名)无法前缀匹配 → 该车系 44 格缺口未覆盖,需真实搜索或人工别名。已记入待办。

## 三、待相关线核实(非本工作流引入)

### Q1 台账 161 条"双源更正"与门禁回退记录不一致
台账现有 463 条懂车帝来源记录:302 条`媒体参数补全` + 161 条`双源更正`。但门禁整合记录(74c0da5)称 est 红修 153 格"试行失控整批回退",回退条目 seq 46638。若已回退,台账不应留 153 条红修记录(8 T4 + 153 est ≈ 161)。**需向门禁线核实:单元格是否已恢复、台账为何仍留记录**。本工作流未触碰这些单元格。

### Q2 车长=4470 污染面比文档广
底表中 `车长=4470` 共 **100 行**,跨多个车系(五菱 Nano EV、炫界Pro EV、宏光MINIEV 等),而 W7 文档只记 17 条(宏光MINIEV,因整备 685/715 使比值出界)。其余行的整备/车长比值恰在 [0.18,0.70] 内故未被 W7 捕获——**污染面可能是系统性的**(v3.7.3 车长估算系数表),建议纳入车长修复包(T4)的评估范围,而非仅 55/76 行。

### Q3 同车系两种写法形成两个队列条目
`宏光MINIEV` 与 `宏光MINI EV`(带空格)、`哪吒U` 与 `哪吒U;哪吒U-Ⅱ` 等源数据命名不一致,导致同车系拆成多个队列条目(分别搜索、分别打分)。不影响正确性(只补空+唯一值),但浪费抽取配额。建议在队列生成器加归一化(去空格后合并)。

### Q4 部分人审车系因款型过滤无可用数据
比亚迪唐(sid 2869)8 个错误:DCD 该车系款型经动力守卫(排除汽油、BEV 需有电池)后无剩余。属 DCD 数据覆盖问题,非逻辑缺陷;该车系 35 格缺口维持留档。

## 五、抓取层重构(2026-09-22,响应用户"不要局限在 Tabbit"的修正)

### R1 直连通道实测不可用【已定型为设计约束】
对 `www.dongchedi.com/auto/params/<sid>`、`/auto/series/<sid>`、站首页、`m.dongchedi.com` 全部实测:一律返回 `HTTP 200 + Content-Type: text/plain + 空体`(m 站为 "Redirect was cancelled")。结论:边缘 WAF 对非浏览器客户端统一返空,与仓库既有记录(urllib 登录墙 + API 需 msToken/a_bogus 签名)互相印证。**抓取必须发生在真实浏览器会话内**,这是硬约束,不是工具选择问题。

### R2 抓取层抽离为浏览器直抓【已交付】
`extract_browser.js`:在懂车帝官网任一页面控制台运行的独立 JS,用**同源 fetch** 抓搜索页(定 sid)与参数页(取 `__NEXT_DATA__.props.pageProps.rawData`),抽 15 个字段 + 能源类型,每 15 车系自动下载 bundle,localStorage 断点续跑,限速 1.5~3s。零安装、不依赖 Tabbit 或任何 agent 运行时;Tabbit 通道降级为可选备选(数据契约一致可混用)。

### R3 bundle 导入器的两个实测问题【已修】
1. **qkey 失效导致一律误拒**:bundle 的 qkey 可能因队列重建而查不到,`expect_brand` 退化为空 → 品牌校验全部 reject(实例:人审 kw `北汽EU5` 与队列 part `EU5` 前缀不匹配)。修:kw 归一副索引 + 前缀锚定双路查找。
2. **series 字段格式降级**:导入器原先把 `series` 写成字符串,而既有文件是 `{sid,name,brand}` 字典。修:写 `{sid,name}`。已用 14 个真实文件 round-trip 验证 **cars 参数数据零损失、逐款型完全一致**。

### R4 合成数据纪律【已处置】
验证导入链时合成了极星2 的参数数据(数值贴近真实但非官网抓取)。已在隔离副本内完成全链测试,**真实仓库中的合成产物已全部清除**(dcd_s999901.json、mapping auto 条目、fuel_form 条目),`raw/dcd_refill/` 经 git 核实与 HEAD 完全一致。教训:测试合成数据绝不进正式底表——本项目"不臆测"红线对测试数据同样适用。
